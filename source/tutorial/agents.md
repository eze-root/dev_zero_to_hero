原文的核心提醒是：**重新审视 skill 描述、`AGENTS.md` 和具体任务 prompt，避免把模型上下文塞得过满。**

编码智能体已经发展了很长一段路，而且最佳实践仍在快速变化。随着模型能力提高，过去需要大量手把手指导和脚手架才能做好的事情，现在往往已经不再需要那么多约束。

如果过去一年一直在 Codex 这类编码智能体上工作，很可能已经在项目中逐渐积累了大量说明，用来把模型引导到更好的结果。每次模型升级时都值得重新检查这些假设；到了 GPT-6 Astra，这件事尤其重要。

这些说明会以不同形式存在：skills、`AGENTS.md`，以及每一次具体任务的 prompt，都会共同影响模型最终如何完成工作。

## 更好的 Skills

这些说明可以被组织成 skills。可以把 skill 理解为存放在 Markdown 文件中的一组 prompt；它还可以附带资源文件和预先打包好的脚本。一般来说，skill 最适合两类情况：一是围绕某个特定工作流提供指导，二是告诉模型如何正确使用某些应用或工具。

现在很多项目会默认塞入大量 skills。每个 skill 都有名称和描述，这些信息会先进入模型上下文，以便模型判断何时应该调用它们。但实践中有两个常见问题：

- 很多 skill description 写得过长；
- 当 skills 数量太多时，Codex 为了把它们塞进上下文，会缩短这些描述。

结果就是：模型真正看到的每个描述反而变少，更难判断当前任务究竟应该选择哪一个 skill。

更糟糕的是，不同 skill 的描述有时会互相矛盾，或者过度强调“什么时候必须使用我”。这样会导致模型加载与当前任务并没有真正帮助的指令。

一个常见的 skill 创建工作流是使用 `$skill-creator`。OpenAI 最近更新了这个 skill 的指导原则，目的就是缓解实践中已经观察到的这些失败模式。

### 让描述尽可能短，并明确说明适用边界

skill description 应该尽可能简短，同时必须清楚表达：**它到底在什么情况下才应该被使用。**

一个不好的数据库 skill，会把触发条件写得非常宽，例如只要任务碰到数据库、查询、模型或持久化，就要求加载“数据库迁移”相关指导。这样模型可能在任何数据库任务里都把 migration skill 拉进来，即使它根本没有要处理迁移。

更好的写法是把边界缩小到真正相关的任务，例如：只有在新增或修改数据库迁移，或者审查迁移上线过程时，才使用这个 skill。

这里的关键不是把描述写得“更完整”，而是让它更准确地回答一个问题：**什么时候需要我？**

### 使用渐进式披露，而不是一次性塞入全部上下文

一个真正好用的 skill，重要特征之一是 **progressive disclosure（渐进式披露）**。

读取一个 skill 本身就会占用上下文，会让会话更快接近 compaction，也可能把与当前任务无关的指导带进来。因此，如果一个 skill 内部包含多种工作流，不要让根文档承担所有细节。

更好的做法是：

- 根文档只做一个最小化的 router；
- 在根文档里告诉模型有哪些支持文档和脚本；
- 只提供足够的信息，让模型知道接下来该去哪里看；
- 不要强迫模型预先读取此刻用不到的内容。

也就是说，让模型按需加载知识，而不是一开始就把所有东西铺满上下文。

### 少写“超详细操作手册”

过去很多 skills 会写成非常复杂的 itinerary 或 recipe：一步一步规定先做什么、再做什么、每一步必须怎么做。

随着模型能力提升，这种写法的收益已经下降。模型现在更擅长理解细微差别和模糊任务，因此过去可能有帮助的过度具体说明，现在反而可能限制结果。

不要因为旧模型曾经需要大量脚手架，就默认新模型也需要同样程度的手把手约束。

### 考虑不同模型会如何读取同一套 Skill

仓库里的 skills 不只服务于你自己的智能体，它们也会影响其他贡献者使用的智能体，而对方可能使用不同模型。

某些对 GPT-5.6 Sol 或 GPT-5.6 Luna 很有帮助的指导，可能会把 GPT-6 Astra 约束得过死。因此，留下长期存在于仓库中的说明时，需要考虑：**未来究竟会有哪些模型读取这些规则？**

## 保持 `AGENTS.md` 与当前模型能力同步

`AGENTS.md` 的特殊之处在于，只要模型在你的仓库里工作，这些规则就会持续生效。因此，应该经常重新审视里面的每一条指令，并问自己：**它现在还真的有必要吗？**

### 不要要求模型在每次小改动之前先读完整套文档

如果只是修一个拼写错误，却要求模型在每次编辑之前先阅读架构文档、数据库文档和部署文档，这显然过度了。

GPT-6 Astra 已经能够自行判断当前任务需要阅读什么，不必在每一次改动前都被强制要求重新浏览整个项目。

更好的做法是给出**上下文化的文档指引**。例如：

- 涉及服务边界时参考 `architecture.md`；
- 涉及 schema 变更时参考 `database.md`；
- 准备部署时参考 `deployment.md`。

也就是说，不要写“任何改动之前都必须把这些文件全部读完”，而应该告诉模型“什么问题对应什么文档”。

当然，这种方式有一个前提：**这些文档本身也必须保持更新。**

如果强制模型在每次编辑前先读一堆文件，最直接的结果就是浪费上下文、拖慢工作速度。

### 不要机械复制旧模型时代的“必须测试”规则

以前的模型常常需要被明确提醒：运行测试、检查结果、确认自己做对了。

GPT-6 Astra 通常会主动做这些事情，因此同样的旧规则现在可能造成重复测试或不必要的验证步骤。

这并不是说测试不重要，而是应该重新判断：**这条指令是在补模型能力缺口，还是已经变成冗余约束？**

### 对安全工作流，可以明确授权它继续做完

GPT-6 Astra 很细致，但相比某些旧模型，它在“一个任务到底应该做到多远”这件事上可能更谨慎。有时它需要一点明确许可，才会继续把任务彻底完成。

对于你已经知道安全的固定工作流，可以在 `AGENTS.md` 中直接给它权限。例如，本地测试如果全部使用一次性 fixture，而且完全没有生产环境访问，那么可以明确告诉模型：

> 本地测试只使用可丢弃的测试数据，并且无法访问生产环境。可以直接运行测试；如果本次改动导致失败，就修复并重新运行受影响的测试，不需要每一步都停下来请求批准。

这种规则比笼统写“凡事先问我”更有效，因为它把**安全边界**和**允许自主完成的范围**同时说明白了。

## 决策边界

描述边界时要特别小心。

如果旧模型过去曾经在未经许可的情况下替你做得太多，你可能会在规则里加入非常强的措辞，要求它每一步都必须先询问。这类约束有时确实有用。

但 GPT-6 Astra 是 OpenAI 当前对齐程度最高的模型之一，对“什么事情在知道安全之前不应该做”有更好的判断。因此，应该按这种能力水平去设计规则，而不是继续沿用针对旧模型缺陷写下的所有防护语句。

如果以前某些边界只是为了防止旧模型“走太远”，而现在你已经切换到 GPT-6 Astra，就值得重新审视这些措辞。Astra 可能会非常认真地服从这些限制，结果在你其实希望它继续推进的地方提前停下。

换句话说，边界应该表达真实的决策需求，而不是历史遗留的模型恐惧。

## 持续性：把“完成”的定义说清楚

如果已经习惯 GPT-5.6 Sol 接到一个请求后持续工作很长时间，那么 GPT-6 Astra 在“什么时候该停”这件事上可能显得更谨慎。

它有时会完成第一个可用实现，然后返回让你检查，即使后面其实还有明显工作没有结束。

解决办法是在任务开始前就定义清楚什么叫“完成”。

如果任务真正的目标包括：

- 把实现跑起来；
- 检查运行结果；
- 修复实际暴露出来的问题；
- 再验证受影响部分；

那么就把这些直接写进请求里。不要假设模型会自动把“写完第一版代码”和“完整完成任务”理解成同一件事。

反过来，如果你的 prompt 要求“第一版实现之后先停下来让我 review”，模型自然会倾向更早结束。因此需要确认：这个 review checkpoint 真的是你必须做出的决策，还是只是以前留下来的工作习惯。

如果希望模型在第一轮结果之外继续探索，也要明确两件事：

- 还希望它继续探索什么；
- 探索到什么边界就应该停止。

## 结论

新模型发布，是一次清理旧规则的好机会。

但不需要手工逐条审查所有内容。可以直接让 GPT-6 Astra 根据本文讨论的原则，审计项目中的 skills、`AGENTS.md` 和任务 prompt：找出过长、重复、互相冲突、过度限制、无条件加载上下文，或者来自旧模型时代但已经失去必要性的说明。

清理完这些历史脚手架之后，再去尝试构建以前因为智能体能力不足而不敢做的东西。
