第八讲：代码之外¶

官方 notes：Beyond the Code
视频：YouTube

备注

优秀的软件工程不止是写出能工作的代码，还包括为失去当前上下文的人清楚地记录理由、尊重维护者时间、有效评审和提问，并对 AI 的使用保持诚实。

单向沟通：写下“为什么”¶

代码通常已经说明“做了什么”，注释更应保存难以从实现推断的理由。高价值注释包括：带上下文和触发条件的 TODO、算法或规范的永久链接、正确性论证、耗时排查得到的教训、常量来源、承重实现细节，以及“为什么没有采用显而易见方案”。过时注释比没有注释更危险，改变相关实现时应同时更新。

README 是多数人的第一入口，应尽快回答：它做什么、为什么值得用、如何使用、如何安装。由浅入深，先让读者看到结果，再承担安装成本。

提交信息是代码库的历史记录。复杂改动的正文可采用“问题 → 方案 → 影响”：什么迫使改变，为什么选这个方法，权衡和意外后果是什么。提交应是能独立理解和评审的一项连贯变化；用 git add -p 分开重构、功能与无关修复。LLM 能根据 diff 描述“改了什么”，但若没有额外上下文，它无法知道真正的“为什么”。

尊重读者也意味着克制：细节应随复杂度增长，简单错字无需长篇论文。

贡献：提高信噪比¶

用户远多于贡献者，贡献者又远多于维护者，维护时间是稀缺资源。高质量 bug 报告应包含环境、预期与实际行为、精确复现步骤和已尝试方法；先搜索现有 issue，尽量构造最小复现。安全漏洞应按 SECURITY.md 私下报告，而不是公开 issue。

贡献代码前阅读 CONTRIBUTING.md 和许可证，先从小改动熟悉流程。PR 只包含必要变化，说明理由、测试方法、权衡和需要重点审查处。维护者接受的是长期维护责任，因此完全可能拒绝“能用但不值得维护”的功能。反馈针对代码而不是人格；不理解时问清楚。

AI 能快速制造外观合理的 PR，却不会把理解和维护责任转走。提交者必须能解释代码、完成测试和清理，否则只是把成本转嫁给维护者。

评审：让反馈可执行¶

评审者应评论代码而非作者，提出具体可执行的建议，解释原因，并区分阻塞问题和偏好。用问题暴露假设，例如“这里为 null 时会发生什么？”，通常比命令式否定更利于讨论。也要肯定做得好的部分，并知道何时停止无价值的细枝末节。

评审既捕获 bug，也传播上下文，是快速学习他人思路的方式。AI 可做第一轮模式检查，但缺少产品语境和责任，不替代人类评审。

提问与教育¶

好问题先陈述自己的理解和调查，缩小到可回答的具体点；必要时用是/否问题校准模型。遇到术语不懂就打断，自己不知道就坦白“不知道，但我可以查”。不要因为第一次回答不完整就假装理解，继续追问直到能够复述和应用。这些规则同样适用于向 LLM 提问。

AI 礼仪¶

AI 对成果有实质贡献时应披露，并说明贡献范围：“整个应用由 vibe coding 完成”和“只用于前端样式初稿”会触发不同审查。遵循团队、项目、合规和数据驻留政策。

学习任务中，AI 直接给出终点可能破坏练习目的；面试和考核评估的是被允许范围内的个人能力。规则不明确时先询问，明确禁止外部工具时就不要使用。

Exercises¶

练习 77 (寻找有价值的注释)

浏览 Redis、curl 等知名项目，找到 TODO、外部参考、“为什么不”或排错教训类注释，并说明删除它会损失什么。

解答 练习 77 (寻找有价值的注释)

答案应提供固定 commit 的永久链接、注释类型、关联代码和它保存的隐含知识。判断标准不是长度，而是该信息能否从代码直接恢复；若删除后读者可能重复失败方案、破坏承重约束或无法验证来源，就是高价值注释。

练习 78 (改写薄弱提交信息)

在开源项目历史中各找一条解释“为什么”的好信息和一条只写“做了什么”的弱信息；结合 diff 用“问题 → 方案 → 影响”改写后者。

解答 练习 78 (改写薄弱提交信息)

改写必须忠于能验证的证据；diff 无法恢复动机时应明确标注未知，而不是编造。理想正文让半年后的读者理解触发问题、选型理由、兼容/性能风险与验证方式。这个练习也说明为什么动机应在提交当时记录。

练习 79 (比较三个高星项目的 README)

比较三个 1000+ stars 的 GitHub 项目 README，判断哪些内容有用、哪些主要是噪声。

解答 练习 79 (比较三个高星项目的 README)

用同一量表比较：首屏能否回答用途/价值；是否先给可运行示例；安装是否可复现；平台与版本要求是否明确；文档和贡献入口是否清楚；徽章、营销图和重复说明是否挤压关键信息。星数不是 README 质量证明。

练习 80 (评估一个开放 issue)

选择真实开放 issue，按环境、预期/实际、复现、已尝试方法和最小复现评估它是否尊重维护者时间。

解答 练习 80 (评估一个开放 issue)

输出一张“已有/缺失/如何补充”的清单，并检查重复 issue、贡献模板与安全披露规则。若要留言，只补充真实的新信息；不要为了完成练习给维护者制造通知。

练习 81 (构造最小复现)

选择遇到的 bug，逐步删除无关部分，得到仍能稳定触发问题的最小案例，并记录删除过程。

解答 练习 81 (构造最小复现)

固定环境和输入，每次只删一类因素并重跑；最后提供从空目录可执行的命令、最小文件、期望/实际输出和复现率。记录哪些删除使问题消失，这些边界本身就是定位根因的证据。

练习 82 (评估一次真实代码评审)

找一个含实质评审意见的已合并 PR，判断哪些评论有效；站在作者角度评估体验。

解答 练习 82 (评估一次真实代码评审)

逐条标注 correctness、安全、设计、可维护性或 nit；判断是否具体、解释原因、给出优先级并保持尊重。还要观察作者如何回应、讨论是否被代码/测试证据解决。好的评审不等于意见越多越好。

练习 83 (比较 Stack Overflow 问题)

在熟悉的技术中比较一条高票问题和一条关闭/低票问题，判断结果能否由本讲建议预测。

解答 练习 83 (比较 Stack Overflow 问题)

比较标题是否具体、是否含最小复现和环境、预期与实际是否清楚、是否展示调查、是否可客观回答、格式是否便于阅读。也要考虑发布时间、受众规模和重复问题等混杂因素，不能把投票完全归因于写作质量。
