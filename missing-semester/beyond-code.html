第八讲：代码之外¶

官方 notes：https://missing.csail.mit.edu/2026/beyond-code/
视频：YouTube

备注

本文依照 Missing Semester 2026 官方 notes 的原文结构完整翻译；保留标题层级、命令示例、工具链接、引用与提示。练习采用 MyST exercise，并在官方题目之外补充折叠参考答案。

成为一名优秀的软件工程师不仅仅是编写有效的代码。它是关于编写其他人（包括未来的你）可以理解、维护和构建的代码。它涉及清晰的沟通、深思熟虑的贡献以及成为您所参与的生态系统（无论是开源的还是专有的）中的好公民。

单向沟通¶

许多软件工程涉及到为那些缺乏你当前背景的人写作：后来加入的队友、继承你代码的维护者，或者六个月后你忘记了为什么做出特定选择的你自己。对于所有此类写作的一个关键建议是，您的目标是捕捉和传达“为什么”，而不仅仅是“什么”。 “什么”往往是不言自明的，而“为什么”是来之不易的知识，很容易随着时间的流逝而消失。

也许工程师之间最常见的沟通形式（除了代码本身）是代码注释。我个人发现很多代码注释是没有用的。但他们不必如此！好的注释解释了代码本身无法解释的事情：为什么某件事以特定的方式完成，而不是解释如何工作（后者通常已由代码表达）。它们可以避免数小时的混乱，而不好的评论会增加噪音，或者更糟糕的是，产生误导。

几乎总是有价值的评论类型：

  • TODOs：标记不完整或尚未打磨的代码，但保留足够的代码 供其他人了解哪些内容尚未完成以及为何被推迟。 “TODO：优化”没有用； “TODO：这个 O(n²) 循环对于 n<100 来说很好，但如果我们扩展，则需要索引”是可行的。

  • 参考：当代码实现时链接到外部源 来自论文的算法，改编来自其他地方的代码，或对文档中指定的行为进行编码。使用永久链接。请注意与参考文献的任何差异。

  • 正确性论证：解释为什么产生不平凡的代码 正确的结果。代码显示了步骤；评论解释了为什么这些步骤有效。

  • 惨痛的教训：如果您花了 30 多分钟调试某些东西 修复方法是一个不明显的咒语，记录下来。过去的你并没有意识到这是必要的；未来的读者也不会。

  • 常量的理由：幻数值得解释。为什么 为什么是 1492？为什么是 16 位？它是随机选择的、来自测试的还是正确性所要求的？即使是“任意选择”也是有用的信息。

  • 承重选择：如果正确性取决于 看似无辜的实现细节（例如，“必须是 BTreeSet，因为下面的迭代顺序很重要”），明确地调用它。

  • “为什么不”：当你刻意避免明显的方法时， 解释为什么。否则稍后会有人“修复”它并破坏东西。

README（你有一个，对吧？）也是与其他开发人员常见的第一个接触点。一个好的人会立即回答四个问题：这是做什么的？我为什么要关心？我该如何使用它？我该如何安装它？按照这个顺序。将其结构像一个漏斗：顶部有一行文字，也许还有一个视觉演示，这样人们就可以在几秒钟内决定这是否可以解决他们的问题，然后逐步增加深度。在安装前显示使用情况——人们希望在执行安装步骤之前了解他们所得到的结果。

提交消息是另一种经常被忽视的“为他人写作”。它们通常被写为“固定的 blah”或“添加的 foo”，虽然在某些情况下这可能就足够了，但很容易忘记它们形成了“为什么”代码库以这种方式演变的历史记录。当某人（包括您！）运行 git blame 试图理解令人困惑的更改时，良好的提交消息应该给他们答案。

一般来说，提交信息正文应回答：

  • 是什么问题迫使这一改变？

  • 您考虑过哪些替代方案？

  • 有哪些权衡或影响？

  • 这种方法有什么令人惊讶的地方？

显然，你应该根据复杂性来衡量细节。一行错别字修复 只需要一个主题。花了几个小时才完成的微妙的竞争条件修复 debug 值得用段落来解释问题和解决方案。

对于复杂的更改，遵循“问题→解决方案→影响”结构可能会很有用：从强制功能或限制开始，然后解释更改的内容和关键设计决策，然后列出值得注意的后果（积极和消极）。最后一部分特别重要；真正的工程涉及平衡关注点，并记录有意进行的权衡，以防止未来的开发人员认为您错过了问题。

LLM_可以_有助于编写提交消息。但是，如果您只是将其指向您的更改并要求其编写更改的提交消息，那么 LLM 将只能访问“内容”，而不能访问“原因”。因此，生成的提交消息将主要是描述性的（与我们想要的相反！）。如果您首先使用 LLM来帮助您进行更改，那么要求 LLM在同一会话中编写提交可能是一个更好的选择，因为您与LLM的对话本质上是有关更改的丰富背景来源！否则，或者此外，一个有用的技巧是专门告诉LLM您想要一个专注于“为什么”（以及上面注释中的其他细微差别）的提交消息，然后_告诉它查询您是否缺少上下文_。本质上，您的行为就像编码智能体的 MCP“工具”，可用于“读取”上下文。

随着您的更改变得更加复杂，请确保逻辑上分解提交（git add -p 是您的朋友）。每一次提交都应该代表一个可以独立理解和审查的连贯变化。不要将重构与新功能混合在一起或结合不相关的错误修复，因为这会混淆哪些更改修复了哪些问题的故事，并且几乎肯定会减慢对更改的最终审查。它还通过 git bisect 为您提供超能力，但这是另一个故事了。

当您开始更加勤奋地进行技术写作时，请注意一点，并且 更广泛地使用它，确保尊重读者。这很容易 一旦开始就会过度解释，但你必须抵制这种情况 敦促读者不要阅读您所写的内容。解释一下 “为什么”并相信他们能够根据自己的情况找出“如何”。

协作¶

作为工程师，我们的大部分工作时间可能都花在自己的键盘上编码，但我们也有相当一部分时间花在与他人交流上。这段时间通常分为协作和教育，投资于在这两方面做得更好的回报是巨大的。

贡献¶

无论您是提交错误报告，贡献简单的错误修复，还是实现一个巨大的功能，都值得记住，用户通常比贡献者多几个数量级，贡献者比维护者多一个数量级。因此，维护者的时间被严重超额认购。如果您想增加您的贡献发挥作用的可能性，您必须确保您的贡献具有高信噪比并且值得维护者花费时间。

例如，一个好的错误报告通过提供理解和重现问题所需的一切来尊重维护者的时间：

  • 环境：操作系统、版本号、相关配置

  • 您所期望的 vs 实际发生的事情

  • 重现步骤：具体。 “点击按钮”不太有用 比“以管理员身份登录时单击/设置页面上的提交按钮。”

  • 您已经尝试过的：这可以防止重复的建议和 表明您已经做了一些调查

如果您发现安全漏洞，请勿公开发布。联系方式 首先私下联系维护者，并给他们合理的时间来修复 在披露之前。许多项目都有 SECURITY.md 文件或 类似的目的。

确保搜索现有问题。 您的错误或功能请求可能已经被报告，最好将信息添加到现有讨论中，而不是创建重复项。更不用说，它还减少了维护者的噪音。

如果你能想出一个，那么最小的可重复的例子就是黄金。它们为维护者节省了大量的时间和精力，并且可靠地重现错误通常是修复错误中最困难的部分。更不用说，您为隔离问题而付出的努力通常也可以帮助您更好地理解它，有时甚至会导致您自己找到解决方案。

如果您没有立即收到回复，请记住维护者通常是时间有限的志愿者。如果您正在等待他们的回复，几周后礼貌地跟进就可以了；但不应每天催促。同样，“我也是”评论或错误报告只是某些终端输出的复制粘贴，对于吸引您的问题获得响应而言，往往会产生净负面影响。

如果您想贡献代码，您还需要熟悉贡献指南。许多项目都有 CONTRIBUTING.md — 请遵循它。您通常还想从小事做起；拼写错误修复或文档改进是一个很好的第一个贡献，因为它可以帮助您了解项目的流程，而不必在内容上反复进行大量操作。

检查项目使用的许可证，因为您贡献的任何代码都会 属于同一许可证。特别要注意 Copyleft 许可证（如 GPL），要求衍生品也必须开源 如果您触摸它，可能会对您的雇主产生影响！ choosealicense.com还有更多的用处 信息。

当您决定打开拉取请求（“PR”）时，首先确保隔离您真正想要接受的更改。如果您的 PR 同时更改了许多其他不相关的内容，审阅者很可能会将其发回给您，要求您进行清理。这类似于如何将 git 提交分解为语义相关的块。

在某些情况下，如果您有许多看似不同的更改，但启用一项功能都需要它们，则可以打开一个更大的 PR 来捕获所有更改。然而，在这种情况下，提交卫生尤其重要，以便维护者可以选择“逐次提交”审查更改。

接下来，请确保解释清楚变革背后的“原因”。不要只是描述_改变了什么_——解释_为什么_需要改变以及_为什么_这是解决问题的好方法。您还应该主动指出在审核中需要特别注意的变更部分（如果有）。根据 CONTRIBUTING.md 和更改的性质，审阅者可能还希望看到其他信息，例如您所做的权衡或如何测试更改。

我们建议回馈上游项目而不是 “分叉”项目，至少作为第一种方法。分叉（许可证 如果允许的话）应该保留给你想要的贡献 make 超出了原始项目的范围。如果你做 fork，请制作 确保您认可原始项目！

人工智能使快速生成看似合理的代码和 PR 变得异常容易，但这并不妨碍您理解自己所做的贡献。提交你无法解释的人工智能生成的代码会给维护者带来负担，因为他们需要审查和维护甚至连作者也不理解的代码。使用人工智能来帮助您识别问题并生成修复/功能是很好的，只要您仍然进行尽职调查将其完善为有价值的贡献，而不是将该工作传递给（已经超负荷的）维护者。

请记住，对于维护者来说，接受 PR 意味着接受长期责任。他们将在贡献者离开后很长时间内维护此代码，因此可能会拒绝善意但不符合项目方向的更改，增加他们不想维护的复杂性，或者根本没有充分记录需求的情况。作为贡献者，你有责任说明为什么接受贡献值得承担维护负担。

当收到 PR 反馈时，请记住，您的代码不是您自己！ 审阅者试图使代码变得更好，而不是批评你 个人而言。如果您不同意，请提出澄清问题 - 您可能会学到 某事，或者也许他们会的。

评审¶

您可能认为代码审查是高级开发人员所做的事情，但您可能会被要求比您预期更早地审查代码，并且您的观点很有价值。新的眼光会发现经验丰富的开发人员忽视的东西，而不太熟悉代码的人提出的问题通常会揭示出应该记录或简化的假设。

复习也是最快的学习方法之一。您将看到其他人如何解决问题、学习模式和习惯用法，并培养对代码可读性的直觉。除了个人成长之外，评审还可以在错误进入生产之前捕获它们，在整个团队中传播知识，并通过协作提高代码质量。它们不仅仅是官僚管理费用。

良好的代码审查是一项需要随着时间的推移磨练的技能，但有一些技巧可以让它们变得更好更快：

  • 审查代码，而不是人： “这个函数令人困惑”与“你写了令人困惑的代码”。

  • 更喜欢可操作的评论： “你能用配置数据类替换这些全局变量吗”比“不要在这里使用全局变量”更容易解决

  • 提出问题而不是提出要求： “如果 X 在这里为空会发生什么？”比“处理无效情况”更能引发讨论。

  • 解释“为什么”： “考虑在此处使用常量”不如“考虑在此处使用常量，以便我们可以根据环境轻松调整超时”有用。

  • 区分阻塞问题和建议： 明确什么是必须改变的，什么是偏好问题。

  • 承认什么是好的： 指出聪明的解决方案或干净的实现是令人鼓舞的，并帮助作者知道要继续做什么。

  • 知道何时停止： 贡献者只有这么多的时间和耐心，而且并不总是最好地花在处理所有的问题上。专注于大事，并考虑事后自己清理小事。

人工智能工具可以发现某些问题，但它们并不能替代 人工审查。他们错过了背景，不了解产品 要求，并且可以自信地提出错误的建议。他们值得 作为第一步使用，但不能替代有思想的人类 审查。

教育¶

作为工程师，我们的很多非编码时间都花在提出问题或回答问题上，也可能两者兼而有之。在协作、与同事对话或尝试学习时。提出好的问题是一种技能，可以让你更好地向任何人学习，而不仅仅是向完美的解释者学习。 Julia Evans 有一些关于“如何提出好问题”和“如何获得问题的有用答案”的优秀博客文章，值得一读。

一些特别有价值的建议是：

  • 首先陈述你的理解：说出你认为你知道的内容并 问“是吗？”这有助于回答者确定您的实际知识差距。

  • 问是/否问题：“X 是真的吗？”防止切线 解释并且通常会提示有用的阐述。

  • 具体一点：“SQL 连接如何工作？”太模糊了。 “向左吗 JOIN 包含右表没有匹配项的行？”是有责任的。

  • 不懂就承认：不懂就打断询问 条款。这反映了信心，而不是弱点。同样，如果他们问你一些你不知道答案的问题，最好说“我不知道”，并可能接着说“但我认为……”甚至“但我可以找到答案”。

  • 不要接受不完整的答案：继续询问后续问题，直到您 其实明白。

  • 先做一些研究：基本调查可以帮助您提出更多问题 有针对性的问题（尽管同事之间随意提问也可以）。

请记住：精心设计的问题有益于整个社区。他们提出了其他人也需要理解的隐藏假设。

请注意，此建议同样适用于与 LLM！

AI 礼仪¶

随着LLM和人工智能在软件工程中的使用越来越多，周围的社会和专业规范仍在不断变化。我们已经介绍了 智能体编程讲座 中的许多战术考虑因素，但其使用中也有一些“较软”的部分值得讨论。

第一个是，当人工智能对你的工作做出有意义的贡献时，披露它。这与羞耻无关——而是关于诚实、设定适当的期望，并确保最终的工作得到适当级别的审查。披露你使用人工智能的哪些部分也是值得的——“整个项目都是通过 vibe coding 完成的”和“我编写了这个备份工具并使用 LLM 来设计 Web 前端”之间存在有意义的区别。例如，我们使用 LLM来帮助编写一些讲义，包括校对、头脑风暴以及生成代码片段和练习的初稿。

您还需要遵循您在此贡献的团队和项目的规范。有些团队在人工智能的使用方面比其他团队有更严格的政策（例如，出于合规性或数据驻留原因），您不想意外地与之发生冲突。公开您的使用情况有助于防止潜在的代价高昂的错误。

如果您的目标是将学习作为您正在做的工作的一部分，请继续 请注意，如果您有人工智能，可以为您完成全部或大部分工作 弄巧成拙；你可能会学到更多关于提示的知识（也许 查看人工智能输出）而不是任务本身。尤其是当你 学习，重点可能是旅程，而不是目的地，所以使用 人工智能“快速找到解决方案”是一个反目标。

面试和其他评估情况中会出现一个相关的问题。这些通常旨在专门评估您的技能和能力，而不是LLM的技能和能力。现在，越来越多的公司允许你在面试中使用 LLM和其他人工智能辅助工具，只要你让他们在面试中观察这些互动（即，他们也在评估你使用这些工具的技能！），但这些仍然是少数。如果您不确定人工智能辅助是否适用于特定任务，请询问！

不言而喻，如果评估情况明确 明确禁止外部工具，不需要LLM等，你不应该使用它们。 尝试谨慎地这样做而不被抓住会回来 咬你。

Exercises¶

练习 77 (寻找有价值的注释)

浏览 Redis、curl 等知名项目，找到 TODO、外部参考、“为什么不”或排错教训类注释，并说明删除它会损失什么。

解答 练习 77 (寻找有价值的注释)

答案应提供固定 commit 的永久链接、注释类型、关联代码和它保存的隐含知识。判断标准不是长度，而是该信息能否从代码直接恢复；若删除后读者可能重复失败方案、破坏承重约束或无法验证来源，就是高价值注释。

练习 78 (改写薄弱提交信息)

在开源项目历史中各找一条解释“为什么”的好信息和一条只写“做了什么”的弱信息；结合 diff 用“问题 → 方案 → 影响”改写后者。

解答 练习 78 (改写薄弱提交信息)

改写必须忠于能验证的证据；diff 无法恢复动机时应明确标注未知，而不是编造。理想正文让半年后的读者理解触发问题、选型理由、兼容/性能风险与验证方式。这个练习也说明为什么动机应在提交当时记录。

练习 79 (比较三个高星项目的 README)

比较三个 1000+ stars 的 GitHub 项目 README，判断哪些内容有用、哪些主要是噪声。

解答 练习 79 (比较三个高星项目的 README)

用同一量表比较：首屏能否回答用途/价值；是否先给可运行示例；安装是否可复现；平台与版本要求是否明确；文档和贡献入口是否清楚；徽章、营销图和重复说明是否挤压关键信息。星数不是 README 质量证明。

练习 80 (评估一个开放 issue)

选择真实开放 issue，按环境、预期/实际、复现、已尝试方法和最小复现评估它是否尊重维护者时间。

解答 练习 80 (评估一个开放 issue)

输出一张“已有/缺失/如何补充”的清单，并检查重复 issue、贡献模板与安全披露规则。若要留言，只补充真实的新信息；不要为了完成练习给维护者制造通知。

练习 81 (构造最小复现)

选择遇到的 bug，逐步删除无关部分，得到仍能稳定触发问题的最小案例，并记录删除过程。

解答 练习 81 (构造最小复现)

固定环境和输入，每次只删一类因素并重跑；最后提供从空目录可执行的命令、最小文件、期望/实际输出和复现率。记录哪些删除使问题消失，这些边界本身就是定位根因的证据。

练习 82 (评估一次真实代码评审)

找一个含实质评审意见的已合并 PR，判断哪些评论有效；站在作者角度评估体验。

解答 练习 82 (评估一次真实代码评审)

逐条标注 correctness、安全、设计、可维护性或 nit；判断是否具体、解释原因、给出优先级并保持尊重。还要观察作者如何回应、讨论是否被代码/测试证据解决。好的评审不等于意见越多越好。

练习 83 (比较 Stack Overflow 问题)

在熟悉的技术中比较一条高票问题和一条关闭/低票问题，判断结果能否由本讲建议预测。

解答 练习 83 (比较 Stack Overflow 问题)

比较标题是否具体、是否含最小复现和环境、预期与实际是否清楚、是否展示调查、是否可客观回答、格式是否便于阅读。也要考虑发布时间、受众规模和重复问题等混杂因素，不能把投票完全归因于写作质量。
